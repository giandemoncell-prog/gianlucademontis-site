Case study · April–October 2026

An AI automation system, built by one person in six months

A network of services that produces content, publishes it across several channels, runs digital products and checks itself every night. It runs on a home PC and a Raspberry Pi that draws a few watts, with cloud AI spending capped at 5 dollars a month.

~280,000lines of code and configuration
28projects under version control
1,300+recorded changes (commits)
1person, working with AI agents

The starting point

Several activities running side by side: multimedia content production, publishing on multiple platforms, digital products, training materials. Each one took hours of repetitive work every week, spread across different tools.

The goal was a system that keeps working with the computer switched off, costs little each month, and reports on its own when something breaks.

The outcome

More activities, not just fewer hours

The hours saved add up, but they are not the main result. On my own, by hand, I could have kept up with one or two of these activities. With automation I run all of them in parallel, every day, even when I am away from the computer.

The system did not make my existing work faster. It made possible work that would not exist without it.

Architecture

Three layers, each with a clear job

Workstation

PC with GPU

  • Mid-sized local AI models
  • Video rendering and heavy jobs
  • Woken remotely only when needed, shut down at night
Always on

Raspberry Pi mini-server

  • Workflow orchestrator (n8n) and scheduled jobs
  • Single gateway to every AI model
  • Small models for sorting and classifying
  • Notification bot, backups, nightly check
External

Cloud services

  • Paid AI models, used only as a fallback
  • Publishing platform APIs
  • Websites and off-site backup storage
Every AI request tries, in order:local PC→low-cost cloud→mini-server

The gateway is described in detail in the article One entry point for all my local AI.

Design choices

Five rules that keep the system standing

Local first, cloud only as a fallback

Most AI work runs on models kept at home. The cloud steps in only when the PC does not answer, with a fixed spending cap and a summary every Monday.

One entry point for every model

Scripts do not know which model they are using. They talk to a gateway that picks one, falls back when needed and tracks costs. Switching provider means editing one file, not thirty.

The heavy machine works on call

The PC does not sit idle waiting. The Raspberry Pi wakes it over the network when there is heavy work, and shuts it down at night when it is idle.

The system checks itself

Every night an automatic check looks at services, disks, backups, expiring credentials and power supply, and sends a summary. Notifications come through a single channel, and only when something needs doing.

Everything is versioned and restorable

Every project is a repository with its own history. Server configuration is under version control and data is backed up off site.

From the field

Real failures and what they taught

The most useful part of the experience was not building. It was learning how an automated system breaks without anyone noticing.

Silence

Two notification bots were down for two and a half weeks. The service kept answering "all good" while no messages went out.

Every send now retries, and the nightly check confirms that messages actually arrive, not just that the service responds.

Never started

One automated workflow showed as created but had never been switched on. Another failed 11 days out of 12 because the external model was overloaded.

Every new automation now gets checked after its first day and has a fallback model.

Wrong time

A morning report arrived at six in the evening: the orchestrator was using New York time.

The time zone is now set explicitly everywhere, never left at the default.

Wrong disk

After a move to a faster disk, some data kept landing on the slow memory card because of a broken link.

When a system folder moves, its sibling folders get checked too.

Expiry

Platform credentials expire every two months and stop publishing without warning.

Expiry dates are recorded and the nightly check warns well ahead.
