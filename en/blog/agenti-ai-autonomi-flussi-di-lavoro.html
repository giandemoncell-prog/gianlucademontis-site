Autonomous AI agents in practice: what I let them do alone, what I don't, and why

For months I have been working with AI agents that keep running when I'm away from the computer: they check the system at night, prepare replies, write drafts, publish. I had to "demote" some of them. Here is the autonomy ladder I use and six real workflows, with the failures that changed them.

In short

An autonomous AI agent is useful when it has few actions available, a clear limit and someone (or something) checking the result. Autonomy is not an on/off switch: it is a ladder. Every workflow starts on the lowest step, climbs only after weeks of evidence and goes down at the first serious incident. Here are the four steps, six workflows I really use and the rules that apply to all of them.

Agent or workflow?

The two words are used as synonyms, but they are not.

  • A workflow runs steps I decided, always in the same order: read the file, prepare the text, publish, notify. Tools like n8n or a simple scheduled script do this.
  • An agent gets a goal and some tools, and chooses the steps on its own: it reads, searches, tries, corrects. Claude Code launched by a program, with nobody watching, is an agent.

In practice almost everything that works is a fixed workflow with an agent inside, only where judgement is needed: understanding a comment, choosing a tone, deciding whether a company is a good fit. The rest (schedules, files, sending, checks) stays plain code that always does the same thing and costs nothing.

The autonomy ladder

  1. Observe and report. The agent reads, analyses and writes a report. It touches nothing.
  2. Prepare, a person approves. The agent writes the draft; publishing or sending stays a human action.
  3. Act within tight limits. The agent acts alone, but only inside a precise boundary: certain posts, a maximum per hour, an end date, a notification for every action.
  4. Act alone. No approval. I keep this for repetitive, predictable steps, and there is almost never an agent there: there is a script.

Two questions decide the step: if it goes wrong, will I see it right away? and if it goes wrong, can it be undone? The more "no" answers, the lower the step.

1. The nightly check: down from step 3 to step 1

Every night at 5:15 a Raspberry Pi launches Claude Code with nobody in front of it. It checks the projects running there (scripts, logs, configuration) and writes a report. At first it could also fix files on its own, with a backup before every change.

It worked, and that was exactly the problem. The fixes stayed on the Pi and never made it back to the main copy of the projects on the PC. After a few weeks the two copies no longer matched, and some of the night-time fixes were lost.

Today the agent is on step 1: report only, with fixes proposed as diffs to apply. The write tools are not forbidden in words in the prompt: they are removed from the configuration it is launched with. I apply the fixes myself, during the day, where they belong. Almost all the value stayed: finding the problem was the hard part.

2. Replies to comments: step 2, with one exception at step 3

When a comment arrives on Facebook, Instagram or YouTube, a service on the Pi prepares a reply and sends it to me on Telegram with two buttons: approve or discard. If I approve, it gets published.

The lesson came one afternoon with 12 drafts in the backlog. I approved them all in less than a minute. Nine were wrong: a small fallback model had written them because the main one had run out of quota. Wrong language, made-up technical details. I fixed them straight away, but the point was clear: the "approve" button gets used as "go", not as a careful review. Quality must be guaranteed before the draft reaches the approver: public texts are written only by large models, and if none is available the draft waits.

For some campaigns with a start and an end date, replies move up to step 3: they go out on their own, but only under that campaign's posts, only if written by a large model, at most 20 per hour, with a notification for each one. Before switching this on I test three or four typical comments, and the instructions say explicitly what not to say.

3. Drafts for job seekers: step 2, by choice

The Claude Code suite for two people looking for work finds companies, verifies contacts, writes tailored letters and leaves them as drafts in their Gmail inbox. It could send them: technically it is easy. It doesn't, and not because I ask it nicely: the sending tools are blocked in the configuration.

A letter to a company cannot be undone. Reading it and pressing "send" takes the person thirty seconds, and that person is the only one who knows whether today they want to write to that company. Here step 2 is not a technical limit: it is the right place. The details are in the article on the suite's architecture.

4. Scheduled publishing: step 4, but no agent

Posts, videos and articles go out at fixed times from a list of scheduled jobs on the Pi, even with the PC off. It is fully autonomous, and rightly so, because it decides nothing: the text is already written and approved, the script takes it to the platform at the set time.

The weak point is elsewhere: a script that says "done" is not proof. The TikTok script, for example, answered "published" when the upload page had changed and the video never went out. That is why, the day after each release, a second program, read-only, checks on the platforms that the content is really there and sends me a summary. Where it cannot check, it tells me so and I verify by hand.

5. The Monday report: no AI

Every Monday at 8 a summary arrives on Telegram: website visits, views on Instagram, Facebook and YouTube, campaign status. It looks like an agent's job. It isn't: it is calls to the platforms' statistics and a few sums. A language model would only add cost and the chance of getting a number wrong.

It is the rule I apply most often: before asking which agent to use, I ask whether an agent is needed. Many questions that sound like AI questions ("did anyone reply?", "what is due today?", "how many visits?") are answered with a search and a date comparison.

6. The workflow that said "published" (and wasn't)

The most instructive mistake was not made by an agent, but by the workflow around it. An n8n workflow published the same content to Instagram, Facebook and LinkedIn in parallel, then sent a notification. The notification failed, and that failure stopped the whole workflow: Instagram, the fastest branch, went out; Facebook and LinkedIn never started. For at least two weeks, without me noticing.

Two rules came out of it: a secondary step (a notification, a log) must never stop the main ones; and the "published everywhere" message is written by whoever checked, not by whoever tried.

Rules that apply to all of them

  • Permissions live in the configuration, not in the prompt. "Don't send" written in the instructions is a prayer. A sending tool that isn't available is a guarantee.
  • Someone else checks the result. A separate read-only program, or a person. Never the agent that did the work.
  • A quantity limit and a brake. How many actions per hour, until when, and what stops it: at the first warning from a platform, the agent stops and says so.
  • What comes from outside is data, not an order. A comment or an email may contain sentences like "ignore your instructions". The agent reads them as content to evaluate, never as instructions.
  • The right model for public text. Small local models are great for sorting, summarising and flagging. To write something other people will read, I use a large model or I wait.
  • Notifications only when there is something to do. If a hundred "all OK" messages arrive, nobody reads the hundred-and-first, the one that matters.

How to start your first workflow

  1. Pick a job you do every week and find boring, not the hardest one.
  2. Write the steps on paper and mark which ones need judgement. Only there will you put an agent.
  3. Start at step 1: for two weeks the agent tells you what it would do, without doing it.
  4. Move to step 2 with a quick approval (a notification with a button) and count how many drafts you correct.
  5. Climb to step 3 only when corrections are close to zero, with a limit, an end date and a separate check.
An autonomous agent is not the one that does the most on its own. It is the one you trust enough not to watch, because you know exactly what it cannot do.

Frequently asked questions

What is the difference between an AI agent and an automation? An automation runs steps a person decided in advance, always in the same order. An agent gets a goal and some tools and picks the steps itself. In practice the best setup is a fixed workflow with an agent only where judgement is needed.

Can you leave an AI agent completely on its own? Yes, but only for small, reversible actions that something else verifies, with a quantity limit and a way to stop it. For anything public or hard to undo, let the agent prepare and a person approve.

Do you need a server to run AI agents? Not to start: a computer and an assistant such as Claude Code launched by hand are enough. A small always-on server, even a Raspberry Pi, helps when the workflow must run at fixed times with the PC off.
